# Отчёт по тестовому проекту: Blog REST API

## 1. Что реализовано

В пустой рабочей папке создан Django-проект с REST API для постов и комментариев.
Использованы Django REST Framework, Simple JWT и drf-spectacular. Список постов
постраничный, авторские поля задаются сервером, черновики и комментарии проходят
контроль видимости. Для локальной работы настроен SQLite, а для PostgreSQL
предусмотрены параметры подключения через окружение. Секретный ключ хранится в
локальном `.env`, который исключён из Git.

Финальные проверки выполнены на Python 3.13.14, Django 5.2.19, DRF 3.18.3,
Simple JWT 5.5.1 и drf-spectacular 0.30.0. Django 5.2 поддерживает Python 3.13.
Опубликованная матрица Simple JWT 5.5.1 пока указывает Django 5.1 и DRF 3.15;
установленная здесь комбинация Django 5.2 и DRF 3.18.3 прошла все 21 тест, но
для неё нет формальной гарантии совместимости со стороны Simple JWT.

## 3. Модели

### Post

- `id` — автоматически созданный первичный ключ `BigAutoField`.
- `author` — внешний ключ к `settings.AUTH_USER_MODEL`, `CASCADE`, обратное имя
  `posts`.
- `title` — обязательная строка до 255 символов.
- `body` — обязательный текст.
- `created_at` — дата создания, заполняется один раз через `auto_now_add=True`.
- `updated_at` — дата изменения, обновляется через `auto_now=True`.
- `is_published` — флаг публикации, по умолчанию `False`.

При удалении пользователя Django удалит его посты благодаря `CASCADE`. Посты
сортируются от новых к старым.

### Comment

- `id` — автоматический первичный ключ.
- `post` — внешний ключ к посту, `CASCADE`, обратное имя `comments`.
- `author` — внешний ключ к пользователю, `CASCADE`, обратное имя `comments`.
- `body` — обязательный текст комментария.
- `created_at` и `updated_at` — автоматически заполняемые даты.
- `is_approved` — признак модерации, по умолчанию `False`.

При удалении поста комментарии к нему удаляются. Комментарии сортируются от
старых к новым. В Django Admin есть действие для одобрения выбранных комментариев.

## 4. Serializers, Views и Permissions

`PostSerializer` принимает `title`, `body` и `is_published`. Поля `author`,
`id`, `created_at` и `updated_at` только для чтения. Автор назначается в
`perform_create()` из `request.user`, поэтому поле `author` из JSON не может
сменить владельца.

`CommentSerializer` аналогично делает только для чтения `post`, `author`, даты и
`is_approved`. Родительский пост и автор передаются в `serializer.save()` из
контекста URL и текущей аутентификации. Одобрить комментарий можно в Django
Admin, но нельзя подменить API-запросом.

`PostListCreateView` и `PostDetailView` отдают гостям опубликованные посты,
авторизованному владельцу дополнительно показывают его черновики. Чужой
неопубликованный пост отфильтровывается и возвращает 404. На опубликованный
чужой пост чтение доступно, изменение и удаление запрещены.

`PostCommentListCreateView` показывает одобренные комментарии, а автору
дополнительно — его ожидающие модерации комментарии. `CommentDetailView`
применяет такую же фильтрацию, а также не раскрывает комментарии к
неопубликованным постам гостям. Добавлять комментарии можно только к
опубликованным постам.

`IsPostAuthorOrReadOnly` и `IsCommentAuthorOrReadOnly` разрешают безопасные
HTTP-методы для уже видимых объектов, а `PUT`, `PATCH` и `DELETE` — только их
автору. `IsAuthenticatedOrReadOnly` отдельно закрывает создание и изменение от
гостей. Скрытые объекты отсутствуют в queryset, а попытка изменить видимый
чужой объект получает 403.

## 5. JWT-аутентификация

Используется Simple JWT с `JWTAuthentication`. Получение пары токенов:

```http
POST /api/v1/token/
Content-Type: application/json

{"username": "имя", "password": "пароль"}
```

В ответе приходят `access` и `refresh`. Access-токен передаётся как
`Authorization: Bearer <access>`. Для выдачи нового access-токена отправляется
`POST /api/v1/token/refresh/` с JSON `{"refresh": "<refresh>"}`. Создание
пользователя в API заданием не требовалось; пользователей создаёт администратор
через Django Admin или `createsuperuser`.

## 6. URL и API

Все основные маршруты имеют версию `/api/v1/`:

| Метод | Endpoint | Доступ |
| --- | --- | --- |
| GET | `/api/v1/posts/` | Гости видят опубликованные, пользователь — также свои черновики |
| POST | `/api/v1/posts/` | Только аутентифицированный пользователь |
| GET | `/api/v1/posts/{id}/` | Опубликованный пост или собственный черновик |
| PUT, PATCH, DELETE | `/api/v1/posts/{id}/` | Только автор поста |
| GET | `/api/v1/posts/{id}/comments/` | Только одобренные; автор комментария видит и свой pending |
| POST | `/api/v1/posts/{id}/comments/` | Аутентифицированный пользователь, пост должен быть опубликован |
| GET | `/api/v1/comments/{id}/` | По тем же правилам видимости комментариев |
| PUT, PATCH, DELETE | `/api/v1/comments/{id}/` | Только автор комментария |
| POST | `/api/v1/token/` | Получение JWT |
| POST | `/api/v1/token/refresh/` | Обновление access-токена |

У списка постов DRF-ответ с `count`, `next`, `previous` и `results`. По умолчанию
10 элементов; `?page=2&page_size=5` выбирает страницу и размер страницы. Размер
ограничен 100.

## 7. Swagger и ReDoc

После запуска сервера:

- Swagger UI: `http://127.0.0.1:8000/api/docs/`
- ReDoc: `http://127.0.0.1:8000/api/redoc/`
- OpenAPI JSON: `http://127.0.0.1:8000/api/schema/`

В Swagger кнопка **Authorize** принимает `Bearer <access-token>`. После
авторизации закрытые POST/PATCH/DELETE-запросы можно выполнять прямо из
интерфейса.

## 9. Запуск проекта

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
test -f .env || cp .env.example .env
```

Вставьте в `DJANGO_SECRET_KEY` в `.env` результат команды
`python -c 'import secrets; print(secrets.token_urlsafe(64))'`, затем запустите:

```bash
python manage.py migrate
python manage.py createsuperuser
python manage.py runserver
```

Для PostgreSQL задайте `DB_ENGINE=postgresql` и заполните `POSTGRES_DB`,
`POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_HOST` и `POSTGRES_PORT`. По
умолчанию используется SQLite.

## 10. Вопросы на защите и ответы

**Почему автор не принимается из запроса?**

Пользователь не должен выбирать владельца объекта. Поля `author` read-only, а
view сохраняет объект с `request.user`.

**Чем отличаются `auto_now_add` и `auto_now`?**

`auto_now_add` фиксирует момент создания один раз. `auto_now` обновляет поле при
каждом сохранении модели.

**Почему для `author` использован `settings.AUTH_USER_MODEL`?**

Это сохраняет совместимость с возможной заменой стандартной модели пользователя
и является рекомендованным способом задавать связи в моделях.

**Зачем одновременно фильтр queryset и object permission?**

Фильтрация исключает недоступные черновики и pending-комментарии из поиска,
возвращая 404. Object permission запрещает изменять уже видимый чужой объект,
возвращая 403.

**Почему новый пост не опубликован, а комментарий не одобрен?**

Это безопасные начальные состояния. Автор может опубликовать пост, а модератор
одобряет комментарий в админке. API не позволяет выдать себе роль модератора.

**Как работает JWT?**

Пользователь получает короткоживущий access-токен и refresh-токен. Access
передаётся в Bearer-заголовке. Refresh используется на endpoint обновления,
поэтому пароль не отправляется при каждом API-запросе.

**Что делает пагинация?**

Возвращает ограниченную страницу результатов и метаданные `count`, `next`,
`previous`. Размер можно менять до заданного максимума.

**Зачем нужны миграции?**

Они версионируют схему БД и позволяют создать или обновить таблицы воспроизводимо
командой `migrate`.

**Как подключить PostgreSQL?**

Выбрать `DB_ENGINE=postgresql` и передать имя БД, пользователя, пароль, host и
port через окружение. Драйвер Psycopg 3 указан в зависимостях.
